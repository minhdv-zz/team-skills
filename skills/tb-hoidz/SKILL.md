## Scope and safeguards

- `/tb-hoidz` authorizes preparation, planning, zones, base mapping, comparison and QA. Combine a concise plan and palette-assignment notice in the brief opening update, then continue without intermediate confirmation; follow the communication rules below. **Stop after the completed base for user approval before detail mapping.** Geometry additions require the user's choice of detail, cut method and triangle cost; existing approvals persist.
- Reuse the supplied concept and target, otherwise selected meshes if unambiguous. Ask only for missing inputs. Never invent a concept, replace the asset or import duplicates by default.
- Record `bpy.data.filepath` at run start as the working save target. Edit the live objects. A changed file starts a new context; an unsaved file requires the user's first save location.
- Every face belongs to a zone; one strip per zone, U collapsed at its center, at least 2 px U/V margins. Combine top-light normals and height, not height alone by default. Use appropriate hard/smooth normals and material response. Preserve geometry during base mapping.
- Store plan, private memberships/evidence, baseline triangles, signatures, QA and exceptions scene-locally. Persistent JSON, image exports and benchmark reports are optional, not default deliverables. `save_plan` defaults to the skill folder: use explicit writable storage instead.

## Base mapping

1. **Connect and prepare.** Call `get_addon_status` once and get compact scene facts: working path, meshes, world bounds, face/triangle counts and materials. Batch independent reads. Import helpers from this skill's absolute scripts directory in each Blender call using them. On first import, put that directory first in `sys.path`, evict gm modules from other paths, reload `gm_core`, and print its verified path/version once (base-api.md). Later calls import without reloading. Run `ensure_palette`; include fallback, relink or material creation in the final report unless it needs a user decision now. Ask before updating a differing team palette's skill copy. The opening update covers palette assignment before `prepare_model(..., assign_material=True)`; avoid a separate routine announcement.
2. **Identify materials before mapping.** In one initial discovery batch where practical, gather parts, bounds, original UV groups and world-space normal summaries for the target objects. Store memberships and evidence privately; summarize only decision-relevant parts. Focus deeper PCA/depth/adjacency checks on ambiguous or mixed parts and representative families, then reuse verified evidence. Additional discovery is allowed for unresolved boundaries. Combine geometric clues with concept position; discovery precedes semantic assignment. Audit uncertain dominant parts before assigning them. A thin bounding box may describe a broad sheet or a diagonal rope: inspect principal dimensions and surface extent plus semantic position. Shape hints are evidence, never material labels. Capture `surface_groups(..., uv_seams=True)` before overwriting UVs on mixed shells. Verify one representative and matching structure before reusing a rule for repeats. Resolve pane/rim, cavity/surface and wrap/mast boundaries during base. Complete the small-part material gate in reference-quality.md for every part or structurally verified family; small size does not exempt a part. Uncertain assignments require focused discovery before mapping.
3. **Plan and assign.** Use reference-quality.md for measured or explicitly estimated concept colors, material and value hierarchy. Batch full-safe-V searches with `suggest_zone_colors`; retain 2–3 candidates and chosen colors privately; emit only a compact tool summary and issues needing a decision. Assign zones from the verified material audit and check unassigned faces and uncertain boundaries before mapping. Do not use a blanket default material to make coverage pass; temporary assignments remain explicitly uncertain until checked. Preserve verified memberships. List missing emblems/planks as future details.
4. **Map and compare.** Apply the plan, then `show_texture(light="FLAT")`. Validate palette and preview material before inspecting color; avoid an initial all-pink screenshot. A pre-map image must answer a specific geometry question: use verified plain solid or temporary zone colors. Inspect one comparable 512–640 px overview after mapping. Complete a semantic boundary review of the audited families, including small fittings and interfaces hidden or unreadable in the overview. Use targeted views only where needed. Correct affected objects/zones only and check neighbors. Optional actual-light fitting is for a concrete unresolved mismatch, not a default whole-asset pass. Another capture must resolve an issue or verify a meaningful correction.
5. **Final QA and save.** Finish planned color and boundary corrections before final QA. During mapping, use compact coverage, boundary and affected-zone checks rather than whole-asset final QA. After the last change, run `qa` and `qa_faces` on every target once. A repair prompted by QA invalidates affected results: rerun the whole-object helpers on affected targets, and expand to all users for shared dependency changes; never save using stale QA. Fix failures; inspect and document intentional warnings/exceptions. Verify coverage, margins, active/render UV, actual palette shader links, normals/light and unchanged base topology. Record reference comparison and material-gate outcome separately: data QA does not prove correct material assignment or visual similarity. Do not mark a base fully verified while uncertain assignments remain; record any genuine reference/topology limitation explicitly. Finalize temporary previews, pack the palette, leave texture visible and execute the guarded save in base-api.md. Report saved path/dirty state, pending details and ask for base approval.
